## 参考回答

一次运行只展示了某一组输入、编译选项、优化结果和目标环境下的一个结果。若代码包含未定义行为，标准没有要求实现保持任何固定输出；编译器还可以基于“程序不会触发未定义行为”的假设重排、删除或合并代码。因此，同一份源码在 `-O0` 和 `-O2`、不同编译器或不同 ABI 下出现不同结果，并不能反推出哪一种行为才是“正确答案”。

可靠的判断路径是：先根据 C 标准定位是否越界、悬空访问、无效移位、错误格式化等未定义行为；再用最小复现和完整编译命令确认诊断；最后在目标平台上记录输入、寄存器/日志和可重复的失败路径。若要证明修复有效，应增加回归测试、边界输入和工具辅助检查，而不是只看一次“正常输出”。

## 评分点

- 能区分“这次输出是什么”和“标准是否定义了输出”。
- 能说明编译器优化假设、目标 ABI 和输入状态会改变表现。
- 能给出最小复现、诊断命令、回归测试和失败证据，而不是只重跑程序。

## 递进追问

1. `-O0` 下稳定通过、`-O2` 下失败时，你会先比较哪些编译产物和警告，而不是直接关闭优化？
2. 如何证明一个修复覆盖了越界路径，而不是恰好改变了堆布局或栈布局？

## 证据边界

C99/C11 标准资料用于判定语言语义；GCC 诊断行为还要绑定 GCC 版本和完整选项。没有目标 ABI、工具链版本和可复现日志时，不对某次输出做平台级结论。
